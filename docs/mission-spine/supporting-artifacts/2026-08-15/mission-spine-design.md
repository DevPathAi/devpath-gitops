## Problem Statement

Leva의 주요 기능은 이미 구현되어 있다. 이번 작업의 문제는 기능 부족이 아니라, 사용자가 랜딩에서 본 약속이 앱의 첫 가치 경험까지 하나의 제품으로 이어지지 않는다는 점이다.

- 정식 랜딩은 light/slate/indigo 기반 편집형 화면이고, Flutter 앱은 warm neutral/ink/amber 기반이다. 메타데이터는 Leva로 바뀌었지만 일부 favicon·설치 아이콘은 Flutter 기본 자산 또는 이전 DevPath 흔적을 유지한다.
- 랜딩은 기능과 LCS 예시를 설명하지만 실제 앱 결과 화면을 충분히 증명하지 않는다. CTA를 누르면 별도 앱의 단순한 트랙 선택 화면으로 이동해 시각적·서사적 연속성이 끊긴다.
- 웹에는 진단, 경로, 콘텐츠, 샌드박스, 멘토가 모두 있지만 화면 단위로 존재한다. 콘텐츠에서 샌드박스로 이동할 때 현재 과제·언어·starter code가 이어지지 않고, 멘토는 “학습 맥락 반영”을 약속하면서도 질문 전에 첨부 맥락을 보여주지 않는다.
- 웹 대시보드는 돌아온 사용자의 다음 학습보다 광고를 먼저 보여준다. 학습 경로는 현재 주차와 미래 주차가 비슷한 시각적 무게를 가져 지금 할 행동이 약하다.
- 모바일은 홈·학습·커뮤니티·알림 중심 companion 구조이지만 웹과 온보딩 서사가 다르고, 공용 디자인 시스템보다 raw Material 컴포넌트 사용 비중이 높다.
- 관리자는 운영 기능을 갖췄지만 고정 4열 KPI, 서버 enum 직접 노출, 중복 컴포넌트 때문에 작은 화면과 한국어 운영 흐름에서 일관성이 떨어진다.
- 문서에는 OAuth 선행/게스트 진단, 2nd Aha, 색상, CTA, 진단 예상 시간이 서로 다르게 남아 있다. 화면을 다시 다듬기 전에 하나의 canonical journey가 필요하다.

따라서 목표는 새 기능을 더하는 것이 아니다. 기존 기능을 `약속 → 진단 → 결과 연결 → 12주 경로 → 오늘의 미션 → 실습·멘토 → 경로 보정`이라는 하나의 시각·행동 축으로 재배치하는 것이다.

## Demand Evidence

- 제품 단계는 사용자가 있지만 아직 유료 고객은 없는 단계로 확인됐다.
- `devpath-home-page`의 주 CTA는 현재 작동 중인 앱의 게스트 진단으로 연결된다. 랜딩과 앱 모두 배포 가능한 제품 자산이므로 순수 아이디어 단계는 아니다.
- 다만 이번 세션에서는 사용자 수, 진단 완료율, 반복 사용률, 실제 관찰 기록을 받지 않았다. 저장소에도 랜딩 CTA와 앱 활성화를 잇는 퍼널 계측 근거가 없다.
- 따라서 “전체 개편이 전환을 높인다”는 주장은 아직 가설이다. 이 문서는 디자인 방향을 고정하고, 기존 사용자를 통한 행동 관찰과 퍼널 기준선을 필수 검증으로 둔다.

## Status Quo

### 랜딩

`devpath-home-page/index.html`은 Hero, 문제 서사, LCS 비교, 작동 방식, 창업자, traction, 요금, FAQ, 리드 폼의 8개 구간을 갖는다. 접근성, 정적 fallback, 지연 hydration, 리드 개인정보 가드는 잘 구축되어 있다.

현재 우회 방식은 “강한 약속을 설명한 뒤 별도 앱으로 보낸다”이다. 실제 앱 스크린과 결과 증거가 약하고, 820px 이하에서 주 내비게이션이 사라지며, Leva 브랜드와 favicon/설치 아이콘이 일치하지 않는다. traction 수치가 없을 때도 제목은 “숫자로 보는 지금”으로 남고, 가격 정보는 코드와 문서에서 서로 다르다.

### 웹 앱

웹은 로그인·동의·게스트 진단과 대시보드·경로·콘텐츠·샌드박스·멘토·커뮤니티·설정·마이페이지를 제공한다. `dp_design`은 셸, 반응형 window class, 상태 화면, KPI, 리스트, 데이터 표, 명령 팔레트까지 충분한 기반을 갖는다.

현재 우회 방식은 각 기능을 별도 페이지로 사용하게 하는 것이다. 사용자는 학습 경로에서 콘텐츠로, 콘텐츠에서 실습/멘토로 이동할 때 “왜 이 과제를 하고 있으며 무엇이 다음 화면에 전달됐는지”를 다시 추론해야 한다.

### 모바일

모바일은 홈·학습·커뮤니티·알림의 4탭 구조다. 전체 웹 기능을 복제하기보다 오늘의 행동, 오프라인 학습, 빠른 기록을 담당하는 companion으로 쓰기에 적합하다. 그러나 웹과 다른 온보딩 서사와 raw Material 기반 화면 골격 때문에 같은 계정의 같은 제품처럼 느껴지지 않는다.

### 관리자

관리자는 사용자·신고·문의·광고 등 운영 기능을 제공한다. 현재 우회 방식은 서버 상태명과 고정 그리드를 운영자가 해석하게 하는 것이다. 사용자 제품과 동일한 브랜드 계약을 쓰되, 장식보다 스캔·필터·우선순위 판단 속도가 기준이어야 한다.

## Target User & Narrowest Wedge

대표 사용자는 취업 준비 중인 한국 Java/Spring 백엔드 초급자 또는 주니어다. 최근 JPA 같은 구체적 과제에서 막혔고, 일반 AI에 현재 수준과 이전 실패를 반복 설명해본 사람이다.

사용자가 전체 범위 개편을 선택했더라도 실행 wedge는 하나다.

> 랜딩에서 진단을 시작한 사용자가 도움 없이 첫 `오늘의 미션`을 열고, 같은 맥락으로 콘텐츠·실습 또는 멘토까지 이동하게 만든다.

모든 화면을 동시에 같은 깊이로 다시 만드는 것이 아니다. 이 대표 여정을 먼저 완성하고, 동일한 계약을 모바일과 관리자에 확장한다.

## Constraints

1. 주요 제품 기능과 백엔드 도메인 범위는 고정한다. 새 기능 대신 기존 정보의 순서·표현·연결·상태를 개선한다.
2. 랜딩은 vanilla HTML/CSS/ES modules, 앱은 Flutter monorepo다. 코드·상태를 직접 공유하지 않으므로 브랜드·토큰 계약을 명시적으로 관리해야 한다.
3. 앱 디자인 기준은 현재 `devpath-frontend/DESIGN.md`의 warm neutral + ink + amber다. 앰버는 성취와 1차 행동에 제한한다.
4. 웹은 전체 학습 workspace, 모바일은 companion, 관리자는 운영 도구다. 픽셀 복제가 아닌 목적별 일관성을 만든다.
5. 기존 loading/empty/error/offline/kill-switch/quota/partial 상태 계약을 유지하고, 정상 화면과 같은 수준으로 설계한다.
6. 본문은 읽기 화면에서 16–18px, 터치 타깃은 최소 44px, 텍스트 대비는 WCAG AA, reduced motion을 준수한다.
7. 랜딩과 앱의 현재 배포 파이프라인을 유지한다. 전체 개편을 한 번에 배포하는 big-bang 방식은 쓰지 않는다.

## Premises

사용자가 다음 전제를 승인했다.

1. **기능 범위 고정:** 새 기능을 만들지 않고 정보 위계, 내비게이션, 카피, 상태 표현, 반응형 구성과 시각 일관성을 개선한다.
2. **대표 여정 통일:** `랜딩 → 게스트 진단 → 로그인/결과 연결 → 12주 경로 → 오늘의 미션 → 콘텐츠 → 맥락형 실습·멘토 → 경로 보정`을 canonical journey로 사용한다.
3. **시각 기준 통일:** 앱의 잉크·앰버 시스템을 공통 기준으로 사용한다. 마케팅 화면만 같은 토큰 안에서 더 표현적으로 구성한다.
4. **채널 역할 구분:** 웹은 전체 학습 작업공간, 모바일은 오늘의 미션·오프라인 학습·빠른 기록 중심 companion, 관리자는 운영 효율 중심으로 설계한다.

## Approaches Considered

### Approach A: Surface Unification

현재 정보구조를 유지한 채 브랜드, 토큰, 아이콘, 타이포, 반응형, 상태 화면을 통일한다.

- Effort: M
- Risk: Low
- Completeness: 6/10
- 장점: 가장 빠르며 기존 라우트와 테스트에 미치는 영향이 작다.
- 단점: 콘텐츠·실습·멘토의 단절과 약한 현재 행동 위계가 남는다.
- 재사용: `dp_design`, 현재 앱 셸, 랜딩의 정적 fallback과 위젯.

### Approach B: Mission Spine

모든 사용자 화면을 `오늘의 학습 행동`으로 수렴하는 하나의 Mission Spine으로 재구성한다.

- Effort: XL
- Risk: Medium
- Completeness: 10/10
- 장점: 랜딩의 약속과 앱의 실제 행동이 이어지고, 제품 차별화인 학습 맥락이 UI에서 보인다.
- 단점: 대시보드·경로·콘텐츠·샌드박스·멘토의 정보 위계를 단계적으로 재배치해야 한다.
- 재사용: 기존 기능·라우트·LCS 데이터·반응형 셸·상태 컴포넌트.

### Approach C: Context Signature

현재 정보구조를 크게 바꾸지 않고 모든 화면에 Context Capsule과 Progress Spine을 대표 시각 요소로 적용한다.

- Effort: L
- Risk: Medium
- Completeness: 8/10
- 장점: 적은 구조 변경으로 Leva만의 인식 가능한 시각 언어를 만들 수 있다.
- 단점: 평평한 정보구조 위에 대표 컴포넌트만 얹은 것처럼 보일 수 있다.
- 재사용: LCS 비교 UI, 경로 진행 데이터, `DpPageHeader`, `DpTag`, KPI·상태 컴포넌트.

## Recommended Approach

사용자는 **Approach B: Mission Spine**을 선택했다.

### Visual thesis

> 따뜻한 종이 위에 오늘의 미션을 검은 잉크로 고정하고, 앰버는 완료할 단 하나의 행동에만 쓰는 학습 작업대.

랜딩은 앱과 똑같이 보일 필요가 없다. 대신 같은 약속, 같은 결과 모형, 같은 미션 언어, 같은 성취 색을 사용한다. 앱은 marketing card wall이 아니라 집중 가능한 workspace여야 한다.

#### High-fidelity visual contract: Mission Ledger

Leva의 시각 서명은 **Mission Ledger**다. 주차, 미션, 사용된 맥락, 다음 행동이 하나의 기록 장부처럼 연결되며 얇은 amber thread가 현재 위치만 표시한다.

- **Composition:** 랜딩은 비대칭 editorial composition과 실제 Outcome Preview를 사용한다. 앱은 Mission Header 아래 본문과 Context Capsule을 정렬하고, Next Action Band가 화면의 유일한 강한 action surface가 된다.
- **Typography:** 새 display font를 추가하지 않는다. Pretendard의 크기·weight·행간 대비로 hero와 작업 화면의 위계를 만들고, 코드·식별자·실행 결과에만 D2Coding을 쓴다. 읽기 본문은 16–18px, 65–75자 measure를 지킨다.
- **Color:** warm paper surface와 ink text가 기본이다. amber는 현재 step, earned completion, 한 개의 primary action에만 사용한다. warning/error/success semantic color를 amber 장식으로 대체하지 않는다.
- **Surface:** 1px hairline과 10px panel radius를 기본으로 하고, nested card를 반복하지 않는다. 같은 배경에서 spacing과 rule만으로 충분한 섹션에는 panel을 추가하지 않는다.
- **Evidence:** hero·diagnostic·claim에서 같은 realistic result fixture와 week/task schema를 사용한다. sample은 sample로 표시하고 live 사용자 결과처럼 꾸미지 않는다.
- **Motion:** amber thread와 state text가 다음 위치로 이동하는 짧은 상태 전환만 허용한다. parallax, count-up, 자동 carousel, 결과를 지연시키는 celebration을 쓰지 않으며 reduced motion에서는 즉시 전환한다.
- **Responsive signature:** amber thread는 Expanded/Large에서 세로, Compact/Medium에서 짧은 가로 progress 또는 text step으로 바뀐다. 의미와 순서는 동일하다.
- **Dark mode:** 별도 neon/terminal aesthetic을 만들지 않고 코드에 정의된 dark warm-neutral token mapping을 그대로 사용한다.

금지 패턴은 purple/blue AI gradient, glassmorphism, 빛나는 AI orb, 3D blob, 과도한 pill, 균일한 카드 벽, 근거 없는 숫자·testimonial, 장식용 dashboard chart다. 이 금지는 랜딩과 Flutter 앱 모두에 적용한다.

### Core interaction model

사용자는 어느 화면에서든 네 가지를 5초 안에 답할 수 있어야 한다.

1. 나는 지금 어디에 있는가?
2. 왜 이 일을 하고 있는가?
3. 어떤 학습 맥락이 사용되는가?
4. 다음에 눌러야 할 한 가지는 무엇인가?

이를 위해 다음 패턴을 사용한다.

| Pattern | Purpose | Primary surfaces |
|---|---|---|
| Mission Header | 현재 주차·과제·완료 조건을 한 문장으로 고정 | Dashboard, Path, Content, Sandbox |
| Progress Spine | 약속부터 경로 보정까지 현재 위치 표시 | Landing demo, Diagnostic, Path |
| Context Capsule | 목표·현재 단원·허용된 최근 실패·다음 보정 공개 | Content, Sandbox, Mentor, Community question |
| Next Action Band | 화면당 하나의 1차 행동과 예상 결과 표시 | 모든 learner screen |
| Outcome Preview | 행동 전에 받게 될 결과를 현실적인 예로 보여줌 | Landing, Diagnostic start, Login claim |
| Evidence Block | 주장 대신 실제 UI·경로·사용자 통제 근거 표시 | Landing, About, Beta |

#### Context Capsule data contract

Context Capsule은 새 데이터 저장소가 아니라 기존 consent·path·content·sandbox·LCS API가 이미 제공하는 필드의 UI projection이다. 전송 전에 수정한 값은 해당 요청 payload에만 적용하며 원본 학습 기록을 바꾸지 않는다. 지원되지 않는 필드는 새 API 없이 UI에 추가하지 않는다.

| Field | Existing source | Purpose | Sensitivity | Default inclusion | Editable before send | Persistence | Community share |
|---|---|---|---|---|---|---|---|
| 학습 목표·트랙 | active path/profile | 질문과 실습의 목표 정렬 | low | ON | request-only summary | 원본 변경 없음 | explicit opt-in |
| 현재 주차·task·content | path/content identifier | 현재 학습 위치 설명 | low | ON | no | 원본 변경 없음 | explicit opt-in |
| 완료 조건 | weekly task/content metadata | 성공 기준 고정 | low | ON | no | 원본 변경 없음 | explicit opt-in |
| 현재 editor code | sandbox editor state | 실행·리뷰 대상 전달 | potentially sensitive | 해당 Sandbox 행동에서만 ON | yes | 요청 payload만 | 기본 공유 불가 |
| 최근 error/output | sandbox/LCS state | 막힌 지점 설명 | potentially sensitive | OFF | yes, opt-in 후 | 요청 payload만 | 기본 공유 불가 |
| 기존 review 요약 | existing review response | 중복 질문 방지 | medium | Mentor 재질문에서만 ON | yes | 요청 payload만 | explicit opt-in |

최근 error/output은 명시적 opt-in 전에는 Capsule, Mentor payload, Sandbox 외부 payload, Community payload 어디에도 포함하지 않는다. Community는 기본적으로 Context Capsule을 전송하지 않으며 사용자가 고른 비민감 필드만 전송 전 preview와 최종 payload에 포함한다.

#### Next Action decision rule

Next Action Band는 가장 진행된 유효 상태부터 결정한다. 우선순위는 `완료된 weekly task → 다음 미션/경로`, `성공한 run과 아직 열지 않은 review → Review`, `사용자가 명시적으로 help를 선택한 현재 interaction → Mentor`, `완료되지 않은 practice → Sandbox` 순이다. Review를 열거나 완료해도 weekly task가 미완료라면 API가 제공하는 완료 조건에 따라 Sandbox 또는 다음 행동으로 돌아간다. API가 필요한 상태를 제공하지 않으면 화면별 추론을 만들지 않고 `Content → Sandbox`, `Sandbox 성공 + review 지원 → Review`, `review 미지원 → 기존 완료/다음 CTA` fallback을 사용한다.

### Canonical journey

```text
Landing promise
  → Guest diagnostic (15 questions)
  → Result preview
  → OAuth/consent to claim the existing result
  → 12-week path with current week foregrounded
  → Today's mission
  → Content
  → Context-aware Sandbox or Mentor
  → Review/result
  → Next mission/path adjustment
```

로그인은 진단을 시작하기 위한 문이 아니라 이미 얻은 결과를 저장하고 이어가기 위한 행동으로 보인다. 미래 12주 전체보다 지금의 1주와 오늘의 1개 미션이 항상 더 강한 시각적 무게를 가진다.

#### Navigation and restoration contract

Mission Spine은 독립 화면들의 링크 모음이 아니라 상태를 보존하는 하나의 학습 작업공간으로 동작한다.

```text
/diagnostic (guest)
  → /diagnostic/result/:resultRef (preview remains visible)
  → /auth + /consent
  → same resultRef restored
  → /path/:pathId/today
  → /mission/:taskId/content/:contentId
  → /mission/:taskId/sandbox
  → /mission/:taskId/review/:reviewId
```

- 랜딩의 모든 1차 진단 CTA는 앱 루트가 아니라 guest-safe 진단 진입점으로 연결한다.
- OAuth 또는 동의가 끝나면 대시보드로 새로 보내지 않고 사용자가 claim하던 동일한 결과 preview로 복귀한다.
- Content, Sandbox, Review, Mentor 간 이동은 `pathId`, `taskId`, `contentId`와 지원되는 run/review correlation을 공유한다. 브라우저·시스템 뒤로 가기는 직전 화면의 스크롤, editor draft, 선택 pane, 공개된 Context Capsule 상태를 복원한다.
- 학습 작업공간의 하위 경로는 shell에서 `Today`를 현재 위치로 읽는다. compact navigation에서 임의의 첫 탭을 selected로 읽지 않는다.
- 유효하지 않거나 만료된 deep link는 로그인 화면이나 빈 Sandbox로 보내지 않는다. 이유를 설명하는 복구 메시지와 함께 Today로 보내고, 사용 가능한 active path가 없으면 기존 Path 생성/재시도 상태로 보낸다.
- 복원에 필요한 식별자가 API에 없으면 클라이언트가 제목·목록 순서로 추론하지 않는다. 해당 CTA를 기존 안전한 상위 경로로 낮추고 projection contract gate를 먼저 해결한다.

#### Emotional storyboard and trust recovery

제품이 만들 감정은 `AI가 놀랍다`가 아니라 `내 상황을 근거로 다음 행동을 믿고 선택할 수 있다`이다.

| Moment | User action | Intended emotion | UI evidence | Trust risk | Recovery behavior |

| Landing | 약속과 실제 결과 모형 비교 | 의심이 구체적 호기심으로 변함 | 실제 12주 경로·이번 주·오늘 미션의 동일 데이터 모형 | canned demo 또는 과장된 시간·성과 | 측정되지 않은 숫자를 제거하고 sample임을 명시 |
| Diagnostic start | track과 산출물 확인 | 낮은 부담, 예측 가능성 | 문항 수, 저장 시점, 받게 될 결과 preview | 가입을 숨긴 bait-and-switch | 결과 전까지 guest임을 명시 |
| Questions | 답변하고 진행 확인 | 작은 진전과 통제감 | progress, 선택 유지, 이전 답변 이동 | 전송 실패로 답변 소실 | 같은 답변·위치를 보존하고 그 자리에서 재시도 |

| Claim / consent | 저장 범위 선택 | 통제권을 잃지 않는 신뢰 | 무엇을 저장·전송하는지와 복귀 지점 | OAuth/동의 실패, guest TTL 만료 | preview와 가능한 pointer를 보존하고 실패 이유를 구분 |
| Path / Today | 오늘 미션 선택 | 장기 계획보다 즉시 집중 | current week, 완료 조건, 한 개의 primary action | 12주 목록·광고가 행동을 압도 | Today를 전경화하고 future weeks를 접음 |
| Content / Sandbox | 학습하고 실패·재실행 | 실패해도 안전한 탐색 | 보존된 code/output, Context Capsule, run 상태 | 빈 Sandbox, context 누락, provider 장애 | 코드·맥락·부분 출력을 유지하고 복구 행동 제공 |
| Review / Mentor | 사용된 맥락과 피드백 확인 | 근거 있는 도움에 대한 신뢰 | 전송된 field, review 근거, 적용 가능한 다음 행동 | generic AI 답변, quota/kill switch | partial response를 보존하고 수동 학습 경로 유지 |
| Path adjustment / return | 다음 미션 또는 보정 확인 | 주도권과 지속 동기 | 무엇이 완료됐고 무엇이 바뀌었는지 diff | 지원되지 않는 보정을 성공처럼 주장 | API 근거가 없으면 단순 `다음 미션`으로 낮춤 |

모든 recovery copy는 `무슨 일이 발생했는가 → 무엇이 보존됐는가 → 지금 할 수 있는 한 가지` 순서로 쓴다. 재진단·재작성·재실행을 첫 복구 수단으로 강요하지 않는다.

#### Mission projection contract

`오늘의 미션`은 새 영속 엔터티가 아니다. 기존 active path, `ThisWeekView`, `PathWeeklyTask`, content, sandbox run/review 데이터를 조합한 UI projection이다. Phase 2에서 repo의 실제 필드명으로 mapping test를 고정하기 전에는 Mission Header, Next Action Band 또는 완료 write를 새로 만들지 않는다.

| UI concept | Existing source/entity | Stable identifier | Derived state | Primary action | Write side effect | Failure behavior |
|---|---|---|---|---|---|---|
| Active path | `LearningPath(status=ACTIVE)` | `pathId` | available / generating / unavailable | 경로 보기 또는 생성 재시도 | 없음 | 마지막 진단·생성 단계 보존 |
| Current week | existing `ThisWeekView` | `pathId + weekNum` | API가 반환한 현재 week; 클라이언트가 날짜로 재계산하지 않음 | 이번 주 보기 | 없음 | 전체 경로로 fallback |
| Today mission | first incomplete `WeeklyTaskView` in API order | `pathId + taskId` | available / in-progress / completed | task의 기존 content 열기 | 없음 | task 식별자 없으면 경로 보기 |
| Mission completion | `PathWeeklyTask.completedAt` / `completed` | `taskId` | incomplete / completed | 완료 표시 또는 다음 task | `contentId`가 있으면 기존 content-progress threshold/write-through, 없으면 `POST /learning-paths/tasks/{taskId}/complete` | 두 경로 모두 owner-safe/idempotent; 성공 시 Today invalidate/refetch, 재시도는 기존 상태 유지 |
| Practice context | content/task/language identifiers + editor state | `taskId + contentId` | ready / running / partial / failed / succeeded | Sandbox 실행 | 기존 run 호출만 | code와 context를 보존하고 재시도 |
| Review | existing `CodeReview.id/status` | `reviewId` 또는 run correlation id | unavailable / pending / partial / ready / accepted | 리뷰 보기/수락 | 기존 review/LCS endpoint가 지원하는 동작만 | partial 결과 보존; 새 상태를 추론하지 않음 |
| Path adjustment | existing LCS/path response가 명시적으로 제공한 보정 | 기존 response/path identifier | none / proposed / applied | 다음 미션 또는 경로 보기 | 기존 API가 지원할 때만 | 지원하지 않으면 문구를 `다음 미션으로`로 낮춤 |

Dashboard, Path, Content, Sandbox, Mentor는 이 projection과 identifier를 공유한다. 데이터가 없을 때 UI만으로 `blocked`, `reviewed`, `adjusted`를 추정하지 않는다.

## Screen Architecture

### Surface coverage matrix

`전체 개편`은 모든 화면을 같은 깊이로 재설계한다는 뜻이 아니다. 모든 현재 route를 아래 셋 중 하나로 분류한다.

1. **Journey redesign:** 구조와 행동 위계를 Mission Spine에 맞게 변경한다.
2. **System conformance:** 정보구조는 유지하고 shell, token, component, responsive, copy, state 규칙을 적용한다.
3. **Explicitly unchanged:** 콘텐츠/법적 의미를 바꾸지 않는다. 시각 conformance만 허용한다.

목록에 없는 새 route는 자동으로 범위에 포함하지 않는다.

### 1. Marketing landing (`devpath-home-page`)

#### Header

- Leva wordmark와 최종 브랜드 마크를 사용한다. 이전 DevPath glyph와 Flutter 기본 아이콘을 제거한다.
- 데스크톱: 작동 방식, 실제 경로, 요금, 개발 기록/소개, 로그인.
- 모바일 header에는 wordmark, primary CTA, 44px menu button을 유지한다. 보조 navigation link는 menu 안에 제공하며 제거하지 않는다.
- Primary CTA 문구는 모든 위치에서 `가입 없이 진단 시작`으로 통일한다.

#### Hero

- Eyebrow: `한국 백엔드 개발자를 위한 AI 학습 사수`.
- Headline: 사용자가 막힌 맥락을 기억하고 다음 미션을 바꾼다는 결과를 말한다.
- Support: 진단 예상 시간, 문항 수, 로그인 시점, 산출물을 숫자로 명시한다.
- Primary CTA: `가입 없이 진단 시작`.
- Secondary CTA: `실제 12주 경로 보기`.
- 우측 영역은 canned 퀴즈보다 `진단 후 받는 것`을 보여주는 실제 앱 형태의 결과 preview를 사용한다. 측정된 시간이 승인되기 전에는 분 단위 약속을 쓰지 않는다.

#### Product proof

- 랜딩용으로 새 가상 UI를 만들지 않는다. 진단 결과, 이번 주 경로, 오늘의 미션, Context Capsule의 실제 앱 컴포넌트를 스크린 또는 DOM mock으로 사용한다.
- `LCS` 약어를 첫 노출에 사용하지 않는다. `현재 목표와 최근 학습을 함께 전달`로 먼저 설명하고 두 번째 노출부터 괄호로 약어를 붙인다.
- Before/After는 일반 AI를 깎아내리는 장식이 아니라, 동일 질문에서 어떤 맥락이 추가되고 다음 미션이 어떻게 달라지는지 보여준다.

#### Trust and conversion

- 창업자 섹션은 lived experience 서사를 유지하되 StockPilot/LearnFlow의 실제 링크, 결과 이미지 또는 검증 가능한 산출물을 붙인다.
- 수치가 없으면 `숫자로 보는 지금` 제목을 쓰지 않는다. `베타 진행 상황`처럼 내용에 맞는 제목으로 fallback한다.
- 요금은 코드·README·디자인 문서 중 하나를 source of truth로 확정하고, 준비 중 tier를 실제 구매 가능 tier처럼 보이지 않게 한다.
- 최종 CTA는 진단으로 보내고, 이메일 폼은 베타 업데이트를 원하는 사용자의 2차 행동으로 둔다.

### 2. Web pre-auth and activation

#### Login and consent

- 로그인 화면은 제품 소개를 반복하지 않는다. `진단 결과 저장`, `기기 간 이어하기`, `학습 경로 생성`처럼 사용자가 얻는 연속성을 말한다.
- 동의 화면은 필수/선택을 시각적으로 분리하고 각 정보가 어떤 화면 경험에 쓰이는지 한 문장으로 설명한다.

#### Diagnostic start

- 6개 트랙 dropdown을 비교 가능한 track cards로 표현한다. 각 카드는 대상, 선수 지식, 12주 산출물 예시를 짧게 보여준다.
- 첫 화면에서 `15문항`, 로그인 없이 시작, 받게 될 결과를 보여준다. 승인된 측정값이 있을 때만 동일 source의 예상 시간을 추가한다.
- 질문 화면은 텍스트 `n/total`과 진행 bar를 제공한다. 남은 예상 시간은 `Measured diagnostic time` gate 승인 뒤에만 표시하며, 승인 전에는 남은 문항 수만 표시한다.
- 선택지는 44px 이상이며 키보드와 screen reader 순서를 보장한다.

#### Result and claim

- claim 전 결과는 기존 guest result가 제공하는 수준 label과 신뢰도만 개인 결과로 표시한다. 강점·보강점은 API가 실제 값을 반환할 때만 노출한다. 첫 3주와 오늘의 미션은 선택 track catalog 기반의 비활성 `결과 형태 preview`로 명확히 표시하며 실제 개인 경로처럼 표현하지 않는다.
- OAuth는 결과 저장 CTA로 표현한다. 실제 미션 진입은 claim과 path generation 완료 뒤에만 활성화한다.
- 경로 생성 실패는 진단 재시작을 요구하지 않는다. `경로 생성 재시도`와 현재 결과 보기 상태를 제공한다.

#### Guest result and claim contract

- 현재 guest 답변·결과의 server lifetime은 마지막 저장부터 30분이며, client pointer `pending_guest_assessment_id`는 같은 browser tab의 `sessionStorage`에 보존한다. OAuth reload/return은 복구하지만 tab/browser session 종료 뒤 복구를 약속하지 않는다.
- 순서는 `result preview → OAuth authentication → required consent → claim commit → path generation`으로 고정한다. 선택 동의 거부는 claim을 막지 않는다.
- Claim 완료와 소유권의 유일한 기준은 PostgreSQL unique `source_guest_id`와 authenticated owner다. Legacy `assessment:claim:*` fast path는 제거하며, 전환기 cache marker가 남아도 권한을 부여하지 않고 DB owner를 재검증한다. 중복 callback·double submit·10초 lock 충돌은 새 assessment/path를 만들지 않고 마지막 성공 단계부터 재시도한다.
- OAuth 또는 consent 실패 시 guest pointer와 server guest result를 TTL 안에서 유지한다. 만료 시 보존되지 않은 것과 재진단 필요를 명시하며 무한 loading을 보이지 않는다.
- 이미 active path가 있는 계정은 기존 path를 자동 교체하지 않는다. 현재 지원 동작인 `기존 경로로 계속`을 제공하고 guest 진단을 path에 merge했다고 표현하지 않는다. 사용자가 기존 경로 이동을 확인하면 pending client pointer를 정리한다.
- Path generation 실패는 claim된 `assessmentId`를 유지하고 generation만 재시도한다. Claim 전 preview의 미션 CTA는 비활성이다.

### 3. Web learning workspace

#### Shell

- Expanded rail: 오늘, 12주 경로, AI 멘토, 커뮤니티. 콘텐츠와 샌드박스는 경로의 하위 작업으로 진입한다.
- Medium: collapsed rail, Compact: bottom navigation. secondary route에서 접근성 selected 상태가 잘못 읽히지 않도록 별도 current-location semantics를 둔다.
- Chrome은 breadcrumb, command palette, 도움 요청, 프로필을 유지하되 현재 미션 제목과 경쟁하지 않는다.

#### Dashboard / Today

- 첫 타일은 광고가 아니라 `다음 학습 미션`이다.
- 순서: 오늘의 미션 → 이번 주 진행 → 최근 피드백/보정 → 연속 학습 → 보조 지표 → 광고.
- 빈 경로 상태에서는 일반 KPI를 숨기고 `진단 시작` 하나를 제시한다.
- 모든 KPI는 숫자보다 사용자 행동을 먼저 설명한다. 예: `이번 주 2/4 미션 완료`.

#### 12-week path

- 현재 주차를 상단 hero로 고정하고 완료 조건·왜 지금 배우는지·다음 unlock을 보여준다.
- 미래 주차는 접힌 roadmap으로 낮은 시각적 무게를 사용한다. 이미 완료한 주차는 증거와 복습 진입을 제공한다.
- 경로 전체의 rationale, 진단 약점과 연결된 이유는 별도 detail panel에서 확인할 수 있다.

#### Content

- 읽기 폭은 최대 70–75자, 본문 16–18px, code는 D2Coding, heading scale과 token color를 `DpMarkdown`에 명시한다.
- Mission Header에 현재 주차, 미션 번호, 완료 조건을 표시한다.
- 하단 Next Action Band는 `이 맥락으로 실습 시작` 또는 `AI 멘토에게 질문` 중 현재 단계의 하나를 primary로 둔다.
- 다음 화면으로 기존 content/task/language/context 식별자를 전달해 선택 언어와 starter code가 일치하게 한다. 새 데이터 모델은 만들지 않는다.
- `contentId`가 있는 task의 완료는 기존 content-progress threshold/upsert가 active path task에 write-through한다. `contentId`가 없는 task만 명시적 task-complete endpoint를 사용하며, 두 경로 모두 성공 시 Today를 invalidate/refetch한다.

#### Sandbox

- 기본 언어 `JAVA`와 Dart starter code가 섞이는 현재 신뢰 결함을 제거한다. 현재 과제의 언어와 starter code를 함께 결정한다.
- Large: task/context, editor, result의 3-pane. Expanded: editor + result의 2-pane. Medium: editor를 기본으로 두고 task/context와 result를 각각 keyboard-accessible side sheet 또는 tab으로 제공한다. Compact: task/editor/result tabs.
- Context Capsule은 현재 목표, 단원, 허용된 최근 실패, 완료 조건을 보여준다.
- 실행 중·부분 결과·quota·provider unavailable 상태에서도 코드를 보존하고 다음 행동을 제공한다.
- accepted run은 `ALLOCATING` session ID를 1초 안에 먼저 보여주고 `RUNNING → COMPLETED/FAILED/KILLED/TIMED_OUT`을 서버에서 영속한다. SSE 연결이 끊겨도 owner recovery로 terminal status와 `truncated` 여부를 복원한다.
- 성공 뒤 primary action은 `리뷰 보기`, 리뷰 뒤 primary action은 `다음 미션에 반영`이다.

#### Review / result

- 새 top-level route가 아니라 Sandbox의 result/review panel 상태로 둔다. direct link가 필요하면 기존 Sandbox route와 식별자 query만 사용한다.
- 실행 결과와 AI review를 분리해 실행 성공을 review 성공처럼 보이지 않게 한다.
- `CodeReview.status`가 pending/partial/ready를 제공하는 범위에서만 상태를 표시한다. `accepted` 또는 path adjustment가 기존 API에 없으면 `다음 미션에 반영` 대신 `다음 미션으로`를 사용한다.
- partial review와 editor code는 재시도 중 보존한다. review identifier가 없으면 같은 run에 새 review를 중복 생성하지 않도록 기존 API의 correlation 규칙을 따른다.

#### AI Mentor

- 빈 화면의 고정 예시 질문보다 현재 미션과 Context Capsule을 먼저 보여준다.
- 전송 전에 첨부되는 맥락을 열어보고 수정할 수 있다. 정제된 최근 오류는 기본 OFF를 유지한다.
- 스트리밍 실패는 이미 받은 답변을 보존한다. 재시도, quota, kill switch를 서로 다른 행동으로 번역한다.

#### Community

- 현재 검색·보드·list-row 구조를 유지한다.
- 질문 작성 시 Context Capsule preview를 제공하고 공유 범위를 사용자가 결정하게 한다.
- feed에서 학습 맥락은 tag처럼 남발하지 않고 질문 해결에 필요한 핵심 두세 개만 요약한다.

## Brand and Design-System Contract

### Source of truth

- 코드 token의 source of truth는 `packages/dp_design/lib/src/theme/`로 둔다.
- `devpath-frontend/DESIGN.md`는 의도와 사용 규칙의 source of truth다. 현재 문서 안의 “문서 SSoT”와 “코드 SSoT” 문장을 이 역할 구분으로 교정한다.
- 랜딩은 앱 package를 import하지 않는다. 아래 semantic contract를 전용 `devpath-home-page/assets/tokens.css`의 CSS custom properties로 mirror하고 token parity test 또는 문서 체크리스트로 검증한다. `assets/styles.css`는 이 파일을 import/consume하며 semantic token 값을 재정의하지 않는다.
- Phase 0 산출물에 versioned semantic token manifest를 포함한다. 각 token은 `Flutter name`, `CSS custom property`, `light value`, `dark value`, `allowed usage`를 가진다. 최소 상태는 default/hover/pressed/focus/selected/disabled/error를 포함한다. Parity test는 이름 존재뿐 아니라 값과 theme mapping을 비교한다.

### Shared semantic contract

| Category | Rule |
|---|---|
| Ground | warm neutral background, white/dark raised surface, three surface levels |
| Ink | primary text and structural border; not pure black everywhere |
| Amber | primary action, current progress, earned completion only |
| Warning | actual warning only; never decorative amber substitute |
| Radius | 10px panels; pills only for compact tags/status |
| Elevation | border and surface hierarchy first; decorative shadow prohibited |
| Typography | Pretendard UI, D2Coding code; learning body 16–18px |
| Spacing | 4/8/12/16/24/32/48 scale |
| Focus | 2px high-contrast focus using `primaryText`, not low-contrast accent |
| Motion | state change explanation only; count-up and transitions respect reduced motion |

### Component ownership and API boundary

Mission 패턴의 **표현과 semantic behavior**만 `packages/dp_design`이 소유한다. repository 접근, 기존 모델 조합, route 선택, telemetry emit, mutation은 web/mobile/admin의 feature 계층이 맡는다. `dp_design`은 네트워크·Riverpod provider·GoRouter를 import하지 않는다.

| Primitive | Presentation input | Required variants / states | Forbidden responsibility |
|---|---|---|---|
| `DpMissionHeader` | eyebrow/week, title, why, completion criterion, progress value/label, status | compact / standard; loading / stale / active / completed | active task 추론, path fetch, 완료 write |
| `DpProgressSpine` | ordered stable step IDs, labels, state, current ID | vertical / horizontal / text fallback; upcoming / current / completed / unavailable | route 이동 결정, 완료 상태 추론 |
| `DpContextCapsule` | ordered field view models: label, value summary, source, sensitivity, inclusion, editability | collapsed / expanded / payload preview; loading / excluded / included / rejected | 원본 profile 수정, raw payload 저장, 암묵적 opt-in |
| `DpNextActionBand` | action ID, label, expected outcome, enabled/disabled reason, pending label, optional subordinate escape | inline / sticky-safe; ready / pending / disabled / retry / completed | 다음 action 계산, navigation, mutation, analytics emit |

- 각 primitive callback은 사용자 intent만 반환한다. feature controller가 projection contract와 Next Action decision rule을 적용한다.
- 같은 route에서 primary action은 최대 하나다. subordinate escape는 text action이며 primary와 같은 시각 무게를 갖지 않는다.
- landing의 `OutcomePreview`, `EvidenceBlock`은 vanilla HTML/CSS component로 유지한다. Flutter widget을 복사하지 않고 versioned semantic token manifest와 동일한 realistic fixture schema만 공유한다.
- web/mobile은 같은 의미의 presentation input을 만들되 플랫폼별 composition을 허용한다. mobile이 raw server enum 또는 별도 onboarding truth를 만들지 않는다.
- widget contract test는 state variant, semantic label, focus order, text scale을 검증한다. feature test는 source data → presentation input mapping과 callback → 기존 action을 검증한다.

### Brand assets

- One Leva mark family: favicon, web PWA 192/512, admin icons, Android launcher, iOS AppIcon, OG image, in-app rail brand.
- 모든 크기에서 `L` 또는 추상 경로/다음 행동을 인식할 수 있어야 한다. Flutter logo와 이전 DevPath `D` glyph를 제거한다.
- 마크가 확정되기 전에는 generic amber square를 새 최종 자산으로 간주하지 않는다.

## Responsive Rules

Width class는 `dp_design`의 기존 breakpoint를 기준으로 고정하고 랜딩 CSS가 같은 경계를 mirror한다. 기준은 viewport의 논리적 width 하나이며 orientation별 별도 breakpoint를 만들지 않는다. 최소 지원 폭은 320px이다.

| Width class | Inclusive range | Navigation | Content | Context Capsule |
|---|---:|---|---|---|
| Compact | 320–599px | bottom nav / mobile menu | one primary column | collapsed bottom sheet |
| Medium | 600–839px | collapsed rail | one or two columns | inline accordion or side sheet |
| Expanded | 840–1239px | full rail | two-column workspace | right rail |
| Large | ≥1240px | full rail | three-pane sandbox / wide dashboard | persistent right rail |

- 47자 사용자명, 긴 한국어 제목, 6개 이상의 track, 12주 roadmap, 빈 지표, 느린 네트워크를 기준으로 레이아웃을 검증한다.
- 모바일 랜딩 내비게이션을 단순히 숨기지 않는다.
- Admin KPI를 width와 무관하게 4열로 고정하지 않는다.

### Accessibility interaction contract

| Pattern / transition | Semantic contract | Focus contract | Responsive / assistive verification |
|---|---|---|---|
| Route and restored route | route마다 고유한 page title과 하나의 level-1 heading; 복구 메시지는 목적지 이유를 먼저 읽음 | 사용자 이동 후 heading, 오류 복구 후 오류 summary 또는 실패한 control로 이동; 뒤로 가기는 이전 control과 scroll 복원 | browser back/forward, deep link, 200% text |
| `DpMissionHeader` | week/task/status/completion criterion을 시각 순서와 같은 순서로 읽고 progress는 label+value 제공 | heading 자체는 프로그램 이동 대상이지만 일반 tab stop은 아님 | 320px reflow, long Korean title, screen reader rotor |
| `DpProgressSpine` | ordered list + 각 step의 completed/current/upcoming text; 색·선만으로 상태 표현 금지 | step이 navigation일 때만 focusable; current step을 임의로 첫 탭 selected 처리 금지 | vertical/horizontal/text variant에서 같은 순서·이름 |
| `DpContextCapsule` | 이름과 expanded/collapsed state가 있는 disclosure; 각 field의 source·included/excluded·sensitivity를 읽음 | 열 때 첫 content가 아니라 disclosure에 유지; modal/sheet payload preview만 focus trap 후 trigger로 복귀 | keyboard, VoiceOver/TalkBack sheet, 200% text |
| `DpNextActionBand` | action label과 예상 결과를 하나의 관계로 읽음; disabled reason을 description으로 연결 | enabled primary가 자연스러운 tab order에 위치; pending 중 focus를 잃지 않음 | sticky/inline 모두 content를 가리지 않고 44px target |
| Loading / partial / success | 반복 progress는 polite, action 실패는 assertive, partial content는 새로 받은 부분만 알림 | skeleton으로 focus 이동 금지; 성공 후 modal 대신 갱신된 status/next action을 announce | reduced motion, slow network, SSE reconnect |
| Menu / side sheet / dialog | 이름·role·open state 제공; 배경 interaction 차단 | open 시 논리적인 첫 control, close/Escape 시 trigger 복귀 | keyboard-only, NVDA, VoiceOver, TalkBack |

- 모든 interactive target은 최소 44×44 logical px이며 focus ring은 2px `primaryText` 계열의 고대비 색을 쓴다.
- 200% text 확대와 platform text scale에서 정보·행동이 잘리거나 겹치지 않아야 한다. horizontal scroll은 code/editor/data table처럼 의미상 필요한 영역에만 허용한다.
- 검증 matrix는 Compact 320/599, Medium 600/839, Expanded 840/1239, Large 1240+ 경계와 keyboard-only를 포함한다. desktop web은 NVDA+Chromium, iOS는 VoiceOver, Android는 TalkBack의 대표 journey를 수동 smoke test한다.
- `prefers-reduced-motion` 또는 platform reduce-motion에서 위치 이동·count-up을 제거하되 상태 설명은 남긴다.

## Interaction and State Matrix

각 route는 아래 state의 적용 여부를 별도 checklist로 표시한다. 적용하지 않는 state는 `N/A`와 이유를 기록한다.

| Surface / trigger | Preserved data | Visible message | Primary recovery | Secondary escape | Retry idempotency | A11y announcement | Telemetry event |
|---|---|---|---|---|---|---|---|
| Diagnostic initial load timeout | selected track | 질문을 불러오지 못함 | 다시 불러오기 | track 변경 | start endpoint 중복 session 금지 | assertive error + focus | `diagnostic_load_failed` |
| Diagnostic answer submit failure | answers, current question, progress | 답변이 저장되지 않음 | 같은 답변 재시도 | 이전 질문/종료 | answer key 기준 중복 방지 | assertive, answer 유지 알림 | `diagnostic_answer_failed` |
| OAuth/callback failure | guest pointer, result preview, claim reason | 결과는 아직 저장되지 않음 | 로그인 재시도 | 진단 결과로 돌아가기 | callback/claim idempotent | assertive + CTA focus | `result_claim_auth_failed` |
| Guest expiry/claim failure | 가능한 local pointer와 preview shell | 30분 만료 또는 claim 실패 구분 | DB-authoritative claim 재시도 | 재진단 | unique `source_guest_id` + owner 기준; cache marker는 권한 근거 아님 | assertive | `result_claim_failed` |
| Path generation partial/failure | assessment, 완료된 SSE stages | 경로 생성의 마지막 성공 단계 | generation 재시도 | 진단 결과 보기 | active path 중복 생성 금지 | polite stage, failure assertive | `path_generation_failed` |
| Dashboard no path | account/profile | 아직 경로 없음 | 진단 시작 | 설정 | N/A | heading focus | `dashboard_no_path_viewed` |
| Content offline | cached content, last local progress | 오프라인이며 sync 대기 | 오프라인 계속 | 경로로 돌아가기 | sync mutation dedup | polite | `content_offline_viewed` |
| Sandbox provider unavailable | editor code, task, Capsule, prior output | 실행 서비스 사용 불가 | 재시도 | code 복사/저장 | run correlation 기준 | assertive, editor focus 유지 | `sandbox_run_failed` |
| Mentor/review quota or kill switch | prompt, partial response/review | quota와 운영 중단을 구분 | 허용 시 재시도 | 수동 학습 계속 | request/review id 기준 | assertive | `ai_surface_unavailable` |
| Community/search empty | query, board, filters | 결과 없음 또는 게시물 없음 구분 | filter 해제/첫 질문 | 경로로 돌아가기 | N/A | polite result count | `community_empty_viewed` |
| Landing traction unavailable | static page, CTA | 정직한 beta 진행 상태 | 진단 시작 | beta update 신청 | N/A | no live announcement | `traction_fallback_viewed` |
| Context field disabled | 나머지 허용 field | 제외된 이유와 현재 전송 범위 | privacy control에서 명시적 활성화 | 해당 field 없이 계속 | request payload snapshot | polite | `context_field_excluded` |

### State precedence and applicability

화면마다 ad hoc 상태를 만들지 않고 다음 우선순위를 공유한다.

1. Shell과 이미 성공적으로 받은 데이터는 route-level 요청 중에도 유지한다.
2. 사용을 법적·운영상 막는 auth/consent, kill switch만 blocking state로 올린다.
3. partial data와 SSE partial response는 usable content로 남기고 실패·재시도를 해당 영역 안에 붙인다.
4. empty는 정상적인 데이터 부재, error는 요청 실패로 분리한다. empty에 `다시 시도`를 기본 CTA로 쓰지 않는다.
5. Mission completion은 서버 확인 후 확정한다. Content-linked progress write-through와 contentless explicit completion을 구분하고, 어느 쪽이든 pending 중 중복 제출은 막되 화면 전체를 잠그지 않으며 실패하면 기존 incomplete 상태와 사용자 작업을 유지한다.
6. success는 celebratory modal로 흐름을 끊지 않고 완료 근거와 갱신된 Next Action Band를 같은 화면에 보여준다.
7. skeleton은 최종 geometry가 안정적인 목록·카드에만 사용한다. 진단 생성·리뷰처럼 단계 의미가 중요한 대기는 실제 stage text와 progress를 사용한다.

| Surface | Loading / pending | Empty | Error / blocked | Partial | Success |
|---|---|---|---|---|---|
| Landing proof | static evidence shell 유지; live metric만 placeholder | 검증된 사례가 없으면 product UI evidence 사용 | live traction만 정직한 fallback | N/A | 진단 CTA와 실제 결과 모형 노출 |
| Diagnostic start | track catalog geometry skeleton | 지원 track 없음 + 운영 안내 | 선택 유지 + catalog 재시도 | cached catalog임을 표시 | 선택 근거·문항 수·산출물 확인 |
| Diagnostic questions | 현재 답변과 progress 유지 | N/A | 같은 답변 재시도; 이전 답변 소실 금지 | 저장 대기와 로컬 선택 구분 | 다음 질문 또는 결과 생성 stage |
| Result preview / claim | preview를 가리지 않고 claim 상태를 inline 표시 | 결과 pointer 없음은 재진단 복구 | preview·guest pointer 유지 | claim은 실패했지만 preview는 계속 읽기 가능 | 같은 preview에 저장 완료 후 Path CTA |
| Path generation | 완료된 stage와 현재 stage 표시 | active path 없음은 진단/생성 CTA | 마지막 성공 stage부터 idempotent 재시도 | 생성된 current week가 있으면 먼저 사용 가능하게 표시 | current week foreground + Today CTA |
| Today / Path | shell과 마지막 mission 유지 | no path / no task를 각각 구분 | last-known mission 유지 + 재조회 | stale 여부를 표시하고 읽기 허용 | 완료 근거와 다음 mission 갱신 |
| Content | cached body와 위치 유지 | 본문 없음은 관리자/지원 경로 | 진행 위치·메모 보존 | 일부 asset 실패를 본문 전체 오류로 승격 금지 | 완료 조건과 Sandbox/다음 행동 갱신 |
| Sandbox | editor·Capsule·prior output 유지 | starter 없음은 빈 editor 사유 표시 | code 보존 + run 단위 재시도 | stdout/review partial 보존 | run 근거 + Review 또는 다음 행동 |
| Review / Mentor | prompt·code·Capsule 유지 | 지원되지 않음과 아직 생성 전을 구분 | quota/kill switch/provider 오류 구분 | 이미 받은 응답 보존 | 사용된 맥락과 후속 행동 공개 |
| Mobile Today | last sync mission 표시 | web에서 만든 path 없음 안내 | offline/sync 실패 구분 | local progress와 server progress 차이 표시 | 동일 task 상태로 동기화 |
| Admin bulk action | 선택 행 유지, 처리 중 행만 pending | 선택 없음은 실행 불가 | 성공/실패 행을 분리 | 부분 성공 summary와 실패 행 재시도 | 결과 수와 변경된 상태 inline 반영 |

상태 화면은 브랜드 일러스트보다 현재 보존된 데이터와 복구 행동을 먼저 보여준다.

## Content and Microcopy Rules

1. 첫 노출에서 `LCS`, `SSE`, `pgvector` 같은 내부 용어를 사용하지 않는다.
2. “AI가 알아서” 대신 어떤 입력이 사용되고 사용자가 무엇을 통제하는지 말한다.
3. 시간 약속은 한 숫자로 통일하고 실제 문항 수·경로 생성 시간을 기준으로 검증한다.
4. 성공은 과장된 축하보다 `무엇이 완료됐고 다음에 무엇이 바뀌는지`로 표현한다.
5. 화면당 primary action은 하나다. secondary action은 outline/text로 낮춘다.
6. 가격·beta 상태·기능 가용성은 현재 코드와 운영 source of truth에서 가져온다.
7. 오류 메시지는 원인, 보존된 것, 사용자가 할 수 있는 다음 행동을 순서대로 말한다.

## Sequencing

전체 범위지만 아래 순서로 하나의 vertical slice씩 완성한다.

### Phase 0: Truth and brand contract

- canonical journey, 가격, 진단 시간, 2nd Aha, 모바일 역할을 문서에 동기화한다.
- Leva logo/icon set과 semantic token contract를 확정한다.
- Phase 0a에서 승인된 funnel event contract만 기존 UI에 instrumentation-only release로 배포하고 event trigger·deduplication·identity alias를 검증한다. Phase 0b에서 기존 UI baseline snapshot과 수집 기간·eligible sample 수를 기록한 뒤 Phase 1 UI 변경을 배포한다. 트래픽 부족 시 descriptive baseline만 남기고 개선율 주장은 보류하되 디자인 구현 자체는 막지 않는다.

### Phase 1: Landing + pre-auth activation

- Landing hero/outcome preview, mobile navigation, product proof, trust, pricing drift.
- Diagnostic track selection, progress, result preview, claim flow.

### Phase 2: Web Mission Spine

- Dashboard/Today, Path current week hierarchy, Content Mission Header/Next Action.
- Context-aware Sandbox and Mentor handoff.

### Phase 3: Mobile companion

- Same account/path continuity, Today-first navigation, shared primitives, Context bottom sheet.

### Phase 4: Admin efficiency

- Responsive KPI, localized status catalog, common table/filter/state patterns.

### Phase 5: Cross-channel design QA

- Brand assets, responsive, dark/light, keyboard, screen reader, reduced motion, long content, empty/error/partial states.
- Landing→first mission end-to-end observation and metric comparison.

## Success Criteria

### User outcome

- 신규 사용자가 랜딩을 본 뒤 5초 안에 `무엇을 받는지`와 primary CTA를 설명한다.
- 관찰 대상 3명 모두 도움 없이 랜딩→진단→결과 claim→첫 오늘의 미션에 도달한다.
- 첫 미션 화면에서 5초 안에 현재 목표, 완료 조건, 다음 행동을 찾는다.
- 콘텐츠에서 실습 또는 멘토로 이동한 뒤 어떤 맥락이 전달됐는지 설명할 수 있다.

### Funnel

- Funnel event contract는 아래로 고정한다. 모든 event는 `occurred_at`, `environment`, `app_version`, `session_id`를 포함하고, claim 시 기존 anonymous/session identity를 `user_id`에 alias한다. 내부 계정·test environment·자동화 UA는 제외한다.

| Event | Exact trigger | Deduplication key | Required identifiers |
|---|---|---|---|
| `landing_viewed` | landing first meaningful render | `session_id + page_view_id` | anonymous/session |
| `landing_diagnostic_cta_clicked` | primary diagnostic CTA activation | `page_view_id + cta_location` | anonymous/session, CTA location |
| `diagnostic_started` | guest/member start API success | `guestId` 또는 `assessmentId` | track, anonymous/user |
| `diagnostic_completed` | complete API success | `guestId` 또는 `assessmentId` | diagnosed level, duration |
| `result_claimed` | idempotent claim success 또는 existing-path branch 결정 | `assessmentId` 또는 `guestId + user_id` | prior guestId, user_id, `claim_outcome: new_path_eligible \| existing_active_path` |
| `path_generated` | path SSE `done` with pathId | `pathId` | assessmentId, user_id |
| `existing_path_continued` | existing-path branch 뒤 기존 path first successful render | `user_id + pathId + originating assessmentId/guestId` | originating assessmentId/guestId, pathId, user_id |
| `path_first_viewed` | generated path first successful render | `user_id + pathId` | pathId, originating session |
| `first_mission_started` | projected first incomplete task opens | `user_id + taskId + first_open` | pathId, weekNum, taskId |
| `first_practice_succeeded` | first mission-linked Sandbox run reaches existing success state | `user_id + taskId + first_successful_run` | pathId, taskId, contentId, run correlation ID |
| `contextual_review_viewed` | mission-linked review first renders with at least one user-approved context field and a resolved Next Action Band | `user_id + taskId + reviewId + first_view` | taskId, reviewId, approved context field count, `next_action_outcome: path_adjusted \| next_mission` |

- 단계 전환율 denominator는 바로 이전 단계의 eligible unique journey다. `path_generated` denominator에는 `result_claimed.claim_outcome = new_path_eligible`만 포함한다. `existing_active_path`는 별도 `result_claimed → existing_path_continued` 전환으로 측정한다. observation window는 24시간이며 Landing CTA 전환만 `landing_viewed`를 denominator로 사용한다.
- `1st Aha`는 new-path journey의 `path_first_viewed`다. 도달률 denominator는 `diagnostic_started` unique journey 중 24시간 안에 `result_claimed.claim_outcome = existing_active_path`로 확인된 journey를 제외한 집합이다. Claim하지 않은 guest journey는 denominator에 남겨 실제 activation drop-off를 보존한다. p50 time-to-value는 이 eligible cohort에서 `path_first_viewed`에 도달한 journey의 `diagnostic_started.occurred_at → path_first_viewed.occurred_at` 차이다. Existing-path journey는 별도 `result_claimed → existing_path_continued` continuity metric으로 보고하며 1st Aha에 합치지 않는다.
- `2nd Aha`는 사용자가 첫 실습 뒤 **본인이 승인한 학습 맥락이 실제 review에 사용됐고, 그 결과 다음 행동이 명확해졌음을 확인한** `contextual_review_viewed`다. eligible denominator는 `first_mission_started` 시점에 기존 API가 Sandbox와 review를 지원한다고 기록된 journey로 고정하며, 나중의 성공 여부로 cohort를 사후 축소하지 않는다. `first_mission_started → first_practice_succeeded → contextual_review_viewed` 전환과 p50 시간을 7일 window로 본다.
- `next_action_outcome = path_adjusted`는 기존 LCS/path response가 실제 보정을 명시한 경우에만 기록·표시한다. 해당 근거가 없으면 review 품질과 무관하게 `next_mission`으로 낮추며 `경로가 보정됐다`고 말하지 않는다.
- Event 수집은 승인된 consent/privacy contract 안에서만 수행하고 각 event dictionary에 consent requirement와 timestamp source를 명시한다.
- 개편 전 기준선이 없으면 Phase 0에서 기준선을 먼저 만들고 임의의 개선율을 약속하지 않는다.
- 기존 요구사항의 1st Aha p50 8분 이내와 도달률 70%+를 제품 상위 기준으로 유지한다.

### Design quality

- 랜딩·웹·관리자·모바일에서 Flutter 기본 아이콘과 이전 DevPath 브랜드 자산 0개.
- semantic token parity checklist 100% 통과.
- 본문·버튼 대비 WCAG AA, touch target 44px, keyboard path, reduced motion 검증 통과.
- Compact/Medium/Expanded/Large에서 overflow 0건.
- 화면별 applicability matrix에서 적용 대상으로 표시된 모든 loading/empty/error/offline/partial/quota/kill-switch 상태를 구현한다. 적용 불가 상태는 `N/A`와 이유를 기록한다.
- 핵심 learner screen에서 primary action이 동시에 둘 이상 경쟁하지 않는다.

## Distribution Plan

현재 존재하는 배포 경계는 보존하되, 없는 파이프라인을 있다고 가정하지 않는다.

- `devpath-home-page`: 현재 Cloudflare Pages direct upload를 사용한다. 앱/backend flag-ON 검증이 끝난 뒤 Landing을 마지막으로 배포하고, 이전 deployment로 되돌리는 절차와 production-`dist` smoke를 릴리스 증거에 포함한다.
- `devpath-frontend/apps/web`, `apps/admin`: 기존 Docker/GHCR/GitOps를 사용하되 build/publish와 promotion을 분리한다. 같은 source SHA라도 flag-OFF와 flag-ON은 `${sha}-mission-off`, `${sha}-mission-on`처럼 서로 다른 immutable tag/digest로 발행하고, 승인된 promotion job이 정확한 digest 하나만 선택한다. 동일 SHA mutable tag 덮어쓰기는 금지한다.
- backend: additive producer와 DB constraint를 consumer보다 먼저 배포한다. schema down-migration은 rollback 수단으로 사용하지 않으며 이전 consumer 호환 필드를 유지한다.
- `apps/mobile`: 현재 repository에 iOS/Android build/release workflow가 없다. ET11에서 signed build gate와 distribution workflow를 만든 뒤에만 Phase 3 mobile을 production 대상으로 간주한다.
- 모든 작업은 각 repository의 최신 `origin/develop`에서 fresh worktree/branch로 시작하고 `develop` PR→검증→릴리스 PR 순서를 따른다. remote HEAD의 `main`/`master`를 자동 base로 사용하지 않는다.
- Phase 0–1, Phase 2, Phase 3을 독립적으로 rollback한다. Release manifest에 OFF digest, ON digest, 실제 promoted digest, prior rollback digest, `deploy order`, `minimum compatible version`, `flag owner`, `contract version`, `rollback trigger`, `migration policy`, 실제 Mentor primary/fallback model을 기록한다.

## Not in Scope

1. 새 AI 모델, 새 교육 전략 prompt, LCS 추천 알고리즘 또는 경로 생성 알고리즘 개발. 승인된 context의 안전한 직렬화·delimiter escaping·평가는 포함한다.

## Engineering Review — Accepted Decisions (approved)

### E1. Delivery shape — full scope, gated vertical slices

- Preserve the approved landing + web + mobile + admin scope; do not big-bang it.
- Slice 1: landing CTA → guest diagnostic preview → OAuth/consent return → durable claim → authoritative current mission/Today → funnel baseline.
- Slice 2: content → contextual sandbox → review/mentor with an explicit, privacy-safe context projection.
- Slice 3: mobile companion, admin conformance, brand assets, and permanent visual/a11y regression coverage.
- Each slice must be deployable and rollbackable without requiring a partially shipped later slice.

### E2. Guest diagnostic claim — database-authoritative idempotency

- Add an immutable `source_guest_id` to the claimed assessment and enforce a database unique constraint.
- A repeated claim returns the existing assessment only when its `user_id` matches the authenticated user; an ownership mismatch is rejected without disclosing the assessment identifier.
- Redis remains the expiring guest-session store and may be used as a cache, but it is not the source of truth for claim completion or ownership.
- Remove the legacy `assessment:claim:*` fast path. If a transitional cache is temporarily retained during mixed deployment, bind `{guestId,userId,assessmentId}`, revalidate the database owner before every return, and apply a bounded TTL no longer than the 30-minute continuation window; cache expiry falls through to the database `source_guest_id` lookup.
- Persist the assessment, items, result, and existing outbox event in one database transaction. Delete the Redis guest session only after commit; a failed cleanup is safe to retry.
- Required failure tests: concurrent duplicate claim, same-user retry after response loss, different-user replay, a legacy/mismatched Redis marker that cannot authorize another user, cache TTL/expiry with database fallback, database rollback before commit, Redis cleanup failure after commit, and expired guest session with/without an already committed claim.

### E3. Current week / Today — extend the existing server projection

- Keep `오늘의 미션` as a projection; do not add a persistent Mission entity or a parallel mission service.
- Evolve `GET /learning-paths/me/this-week` so the server selects the milestone containing the first incomplete task in API order. Do not let web or mobile recalculate a week from dates or the full path document.
- Add stable `taskId` and the existing completion/content fields to `WeeklyTaskView`; expose an explicit `nextTask` and `pathCompleted` outcome instead of making clients infer them from a title.
- If every task is complete, return the final milestone with `pathCompleted=true` and no next task. No-path and malformed-path remain distinct typed outcomes.
- Make dashboard, Path, web Today, and mobile Today consume the same query contract. For a task with `contentId`, preserve the existing content-progress threshold/upsert write-through that completes the active-path task; only a contentless task uses the existing owner-safe, idempotent `POST /learning-paths/tasks/{taskId}/complete` endpoint. Both success paths invalidate and refetch Today.
- Required tests: week-1 start, first content completion advancing `nextTask`, contentless completion advancing `nextTask`, replay/no-op idempotency for both write paths, optional/required ordering according to API order, all-complete path, missing task/content, no active path, stable identifier mapping, and web/mobile contract parity.

### E4. Mentor context — LCS-authoritative, purpose-scoped consent

- Remove the AI service's implicit attachment of the user's five most recent Sandbox submissions. Absence of an approved snapshot means no supplemental learner context is sent.
- Extend the existing LCS draft → preview → commit flow with a validated `mentor_prompt` purpose and private visibility. Do not add a parallel context-preference system to the AI service.
- The mentor request carries only the committed `contextSnapshotId` plus the question/content identifier. The AI service validates snapshot owner and purpose before starting SSE and rejects an invalid or cross-user snapshot without disclosing its content.
- Store the exact fields and immutable snapshot actually used in the existing `AiMentorSession.contextSnapshot`; never place code, errors, output, or snapshot content in routes, analytics, or ordinary logs.
- Low-sensitivity mission/content identifiers may be selected by default according to the approved ledger. Current editor code is opt-in for that Sandbox action only; recent errors/output remain OFF until explicitly selected in the preview.
- Reuse the existing LCS snapshot entity, draft store, preferences, partial-source behavior, and AI mentor session persistence. Add purpose/visibility validation and a user-authorized snapshot-consumption contract; no new persistence model.
- Required tests: no-snapshot/no-context, purpose mismatch, different-user replay, draft expiry, source partial failure, field deselection, recent-error default OFF, current-code one-request scope, and persisted `fieldsIncluded` parity with the provider payload.

### E5. Diagnostic continuation — same-tab, versioned, preview-preserving

- Keep the platform OAuth CSRF/mobile/admin `state` contract unchanged. Same-tab `sessionStorage` is the supported continuation boundary; cross-tab and cross-device recovery are not part of this slice.
- Replace the raw guest-ID value with a versioned `DiagnosticContinuation` envelope containing only `guestId`, track, the actual diagnosed level/confidence preview, `expiresAt`, return stage, and an opaque journey ID. Never store raw answers or provider credentials.
- Model track → questions → preview → auth → consent → claim → saved preview as explicit phases with data preserved across recoverable failures. An error augments the last valid phase rather than replacing it.
- After the database-authoritative claim succeeds, update the authenticated user's onboarding state, render the same preview with saved status, and navigate to Path only from the user's explicit CTA. Clear the envelope on successful handoff, explicit restart, invalid schema, or expiry.
- Distinguish OAuth failure, required-consent block, guest TTL expiry, already-claimed same-user recovery, ownership mismatch, and path-generation failure in controller state and recovery copy.
- Required tests: reload at every phase, OAuth callback twice, consent before claim, failed consent submit, same-user claim replay, storage corruption/version mismatch, 30-minute expiry boundary, router refresh race, and preview equality before/after claim.

### E6. Mission workspace — route IDs plus existing Sandbox/Review persistence

- Add canonical learner routes `/mission/:taskId/content/:contentId` and `/mission/:taskId/sandbox`; keep the existing `/content/:id` and `/sandbox` routes as backward-compatible aliases/standalone fallbacks.
- Resolve a controlled frontend `MissionWorkspaceContext` from route identifiers plus the authoritative current-mission response. URLs contain identifiers only—never editor code, output, errors, prompt text, or context snapshots.
- Wire the existing nullable `contentId` and `codeBlockId` fields into Sandbox requests. Do not add a persistent MissionWorkspace entity or duplicate task state in Sandbox storage.
- Preserve existing `log` and numeric `session` SSE events and add a backward-compatible terminal `result` event containing `sessionId`, persisted `status`, `exitCode`, and `truncated`. Server terminal statuses are `COMPLETED`, `FAILED`, `KILLED`, or `TIMED_OUT`; unavailable and transport-aborted remain typed delivery/admission outcomes and must not be fabricated as execution terminals or collapsed into `RunDone`.
- Add an authenticated, owner-scoped Sandbox session read endpoint for reload/recovery. The in-Sandbox Review panel continues to poll by the existing `sandboxSessionId` and uses the session's terminal status as its evidence.
- If no task-specific starter metadata exists, use a language-correct generic template and label it as such. Never present a generic template as task-specific evidence.
- Required tests: old-route aliases, deep-link/reload/back-forward, route ownership/mismatch, JAVA/NODE/PYTHON starter parity, additive SSE compatibility, each terminal status, aborted stream with persisted session, session owner denial, and Review polling correlation.

### E7. Release architecture — additive producer-first with build-time flag

- Do not add a remote-config service for this program. Add `MISSION_SPINE_ENABLED` to the existing build configuration, default it OFF, and inject the commit/application version into production builds.
- Build and publish distinct immutable OFF and ON artifacts without deployment, even when they share a source commit; their tags/digests must encode compiled flag/config identity and cannot collide. An approved manual promotion job selects an exact digest only after the compatibility smoke, then holds a 15-minute canary before Landing promotion.
- Deploy in this order: shared database migrations → additive learning/LCS/Sandbox/AI producer contracts → compatible frontend OFF digest → contract/browser smoke → approved ON digest promotion → 15-minute canary → Landing build last.
- Consumers must tolerate absent additive fields during the producer-first window. Backend additions remain backward compatible and are not rolled back merely because a frontend rollback occurs.
- Record backend revisions, OFF digest, ON digest, promoted digest, prior rollback digest, GitOps commit, Landing source SHA/deployment, flag/config contract version, approval, canary window, and smoke evidence in one release manifest.
- Roll back in reverse exposure order: restore/redeploy the prior Landing artifact first, point GitOps web back to the release manifest's recorded prior digest, and leave additive schema/API fields in place. No destructive down-migration in an incident.
- The build flag is not an instant kill switch: toggling requires a new immutable image. Existing service-level mentor/sandbox kill switches remain authoritative for those capabilities.
- Required release checks: old frontend against new APIs, flag-OFF new frontend against old/additive APIs, distinct OFF/ON digest assertions, flag-ON smoke, mixed-version response fixtures, manual promotion approval, 15-minute canary, Landing last-deploy guard, and prior-digest rollback rehearsal.

### E8. Funnel analytics — PostHog EU with an explicit identity and privacy boundary

- Use one PostHog EU project as the sink behind two thin `JourneyAnalytics` adapters: vanilla JavaScript for Landing and Dart for Flutter web. Product code emits the shared event contract and does not depend directly on the vendor SDK.
- Capture only the approved, versioned allowlist of Mission Spine funnel events. Disable autocapture and session replay, disable IP collection, and reject unknown properties before they reach the SDK. Code, editor output, errors, prompts, answers, OAuth data, and LCS/context snapshots are never analytics properties.
- Generate a cryptographically random opaque `journeyId` on Landing, persist it only for the browser journey, and hand it to `/diagnostic` with the CTA. The app captures and then removes it from the visible URL. Use this property to correlate the Landing and app events; do not alias separate-origin anonymous IDs.
- After authentication, call `identify` with a stable opaque internal user identifier—never email, GitHub handle, name, or provider subject—and retain `journeyId` as the funnel join key. Call `reset` on logout and shared-device account changes.
- Initialize analytics opted out. Before production baseline collection, the privacy owner must approve either explicit analytics consent or a documented cookieless policy; the chosen mode, PostHog region/project, retention, access owner, and deletion procedure are release-manifest gates.
- Ship the event adapter and current-flow instrumentation before the visual UI changes. Record the eligible denominator and baseline window first; only then expose the Mission Spine UI behind the accepted build flag.
- Required tests: JavaScript/Dart event-name and property-schema parity, unknown/PII property rejection, opt-out default, consent transition, `journeyId` generation/handoff/URL removal, authenticated identify and logout reset, duplicate navigation suppression, internal/test traffic exclusion, and representative funnel replay through `contextual_review_viewed`.

## Engineering Review — Code Quality Decisions (approved)

### E9. Recoverable UI failures — feature-scoped retained-data state

- For Diagnostic, Today, Content, and Mission Workspace, model stable user-visible data separately from the current phase, mutation status, and recoverable failure. A loading or action failure augments the last valid data instead of replacing it.
- Use a full-page loading/error state only when the feature has never produced usable data. Once a preview, mission, content document, editor draft, Sandbox transcript, or Review result exists, preserve it and show the failure at the action/section boundary with a retry.
- Follow the existing `PathState`, `MentorState`, and `MyPageLoaded` precedents with small immutable feature-owned records and `copyWith`. Do not introduce a global `ResourceState<T>` hierarchy or force streaming/composite features into one generic state machine.
- Make retry commands explicit and idempotent. A secondary mutation such as content-progress reporting, analytics capture, Review refresh, or claim cleanup cannot turn a usable primary screen into a blank error screen.
- Required tests: failure before first data, failure after valid data, repeated action while pending, stale response after route change, retry success, content-progress POST failure preserving content, diagnostic claim failure preserving preview, Sandbox stream failure preserving editor/logs, and Review failure preserving terminal run evidence.

### E10. Shared learning-path client boundary — typed `dp_core` API only

Web and mobile consume the same typed request/response models instead of embedding endpoint strings and raw JSON parsing in their controllers; content-linked completion stays behind the existing ContentProgress API boundary.

Remove legacy client-side `milestones.first` and flattened-path selectors once the authoritative producer field is available behind the accepted rollout gate.
- Do not broaden this task into a generic repository framework or migrate unrelated endpoints. `AssessmentApi` is the structural precedent; `LearningPathApi` is the only new shared client required by Mission Spine.
- Required tests: new/old/malformed response fixtures, absent additive fields, stable `taskId`, no-path/path-complete outcomes, owner-safe idempotent contentless completion, content-progress write-through compatibility, web/mobile consumption parity, and a repository search proving Mission surfaces no longer calculate current week independently.

### E11. Mission Workspace state ownership — route-keyed provider families

- Required tests: A→B→A draft restoration, A/B run and Review isolation, late A response while B is visible, deep-link/reload recovery, browser back/forward, provider disposal and subscription cancellation, duplicate route IDs, route/task ownership mismatch, and bounded inactive-workspace retention.

### E12. LCS reuse boundary — purpose-aware data contract, feature-owned UX

- Generalize the existing LCS data adapter around a validated purpose, requested-field allowlist, private/public visibility policy, and draft/commit operations. Community and Mentor consume this common data contract but keep separate orchestration and presentation.

- The AI service consumes only an owner- and purpose-validated committed snapshot ID as accepted in E4. It does not duplicate the LCS field allowlist, preferences, or visibility rules.
- Required tests: existing Community flow unchanged, purpose retained through Redis draft and commit, purpose escalation rejected, different-owner replay rejected, Mentor always private, `recent_errors` default OFF, no snapshot means no supplemental provider context, and exact parity among committed `fieldsIncluded`, persisted mentor context, and provider payload.

## Engineering Review — Performance Decisions (approved)

### E15. Today performance — narrow authoritative read projection

- Implement the authoritative current-mission endpoint as a narrow ordered read projection. Query the active path's tasks, select the first incomplete task in server order, and assemble only that task and its milestone; do not invoke the full 12-week path/diagnosis mapper.
- Do not add Redis caching for this read path in the first release. In web/mobile, share one in-flight request and a 30-second online snapshot across Today consumers; successful content-progress write-through, successful contentless task completion, and successful path generation each invalidate and refetch immediately.
- Start optional dashboard metrics in parallel. Above-fold Today must render from the current-mission response alone and cannot wait for ads, badges, charts, or the full Path document.

### E16. Sandbox/Mentor streaming — bounded resources and durable terminal state

- Replace Sandbox's unbounded common-pool execution with a dedicated bounded executor, one active run per user, explicit queue capacity, and typed 429/503 rejection. Export bounded active/queued/rejected metrics without user or content identifiers.
- Cap combined stdout/stderr at 256 KiB and individual SSE events at 16 KiB; emit `truncated=true` in the terminal result. The web client batches log updates at no more than 20 Hz and retains at most 2,000 rendered lines in a ring buffer instead of copying an ever-growing list per frame.
- After capacity acceptance, commit an `ALLOCATING` session row and stable identifier before starting the runner; best-effort emit the `session` event within one second, transition to `RUNNING`, then execute. A failed emitter is recorded as delivery failure and never throws into or cancels the execution state machine.
- Add an additive shared Flyway migration that extends the status constraint with `TIMED_OUT` and persists an `output_truncated` boolean. Runtime timeout writes `TIMED_OUT` rather than overloading `KILLED`; the terminal `result` event mirrors the persisted status, exit code, and truncation flag, and truncation remains recoverable after reload.
- Persist completed/failed/killed/timed-out status independently of SSE delivery, then best-effort emit the terminal result. A disconnected or failed emitter is a delivery failure, not an execution outcome.
- Add timeout/failure terminal writers and a reconciliation job for stale `ALLOCATING` and `RUNNING` sessions. Target zero accepted sessions in either non-terminal state for more than 35 seconds and alert on any non-zero sustained count.
- Add SSE heartbeat, graceful deployment drain, and bounded sub-timeouts/fallback for supplemental Mentor context/reference calls. Target Mentor TTFT p95 ≤5 seconds and explicit stream terminal outcomes ≥99%.

## Code Quality Implementation Rules

1. Feature state separates retained valid data, phase, mutation, and recoverable failure. A secondary failure cannot replace usable content with a blank page.
2. `dp_core` owns typed wire models/API calls only. Riverpod, route keys, caching, and Flutter UI remain app-owned.
3. Workspace providers are keyed by canonical `taskId + contentId`; all async completions carry the same key/generation and are ignored after mismatch.
4. LCS owns purpose, fields, owner, visibility, draft, and commit policy. Community and Mentor share this data adapter but not presentation/orchestration.
5. All additive wire fields remain nullable for the mixed-version window. Unknown fields are ignored; missing required normalized identity produces an explicit typed fallback, never UI inference.
6. Analytics event/property names come from one versioned contract tested by JavaScript and Dart. Feature code cannot call the vendor SDK directly.
7. Cancellation, timeout, and emitter disposal are explicit for every SSE subscription and bounded executor job.
8. Landing semantic values are owned by `assets/tokens.css`; Landing feature/layout work consumes that file but cannot redefine its values in `assets/styles.css`.

Recommended inline decision comments are limited to these non-obvious invariants:

- claim cleanup occurs after database commit and a Redis failure cannot undo a committed claim;
- a claim cache marker cannot authorize a caller; database owner validation remains mandatory and cache expiry falls back to `source_guest_id`;
- current mission follows producer order and must not use `milestones.first` client inference;
- content-linked completion remains content-progress write-through, while contentless completion alone calls the explicit task endpoint;
- continuation is cleared only by the documented success/restart/invalid/expired transitions;
- route generation protects task A state from late task B/A callbacks;
- Sandbox SSE delivery failure is not an execution terminal result;
- LCS commit cannot change draft owner, purpose, visibility, or selected fields;
- analytics is manual-allowlist/fire-and-forget and cannot control product navigation.

## Regression Tests — Critical

- A guest claim can create at most one owned assessment/path result; a different user never learns or reuses that result identifier.
- A legacy, unbound, expired, or cross-owner Redis claim marker never authorizes a caller; every replay returns only after database owner validation.
- An expired Redis guest pointer with a committed DB row returns the committed owner-safe outcome; cleanup failure is retriable and non-destructive.
- Today always comes from the authoritative producer order; web and mobile do not independently infer current week or first task.
- Content-linked threshold completion and contentless explicit completion each advance Today exactly once; replay is a no-op and non-owner writes are denied on both paths.
- Guest preview remains visible across login, consent, transient claim failure, and callback replay; it is not silently replaced by a gate or redirect.
- Existing-path and new-path cohorts remain distinct in UI behavior and funnel denominators.
- Task A/B drafts, Sandbox runs, Reviews, and late responses never cross route-key boundaries.
- JAVA/NODE/PYTHON language, starter, request, persisted session, and Review correlation agree end to end.
- Every accepted Sandbox run commits a stable session ID before runner start; disconnect never fabricates success or completion, and owner reload recovers durable terminal status plus truncation or a stale-`ALLOCATING`/`RUNNING` reconciliation outcome.
- No LCS snapshot means no supplemental Mentor context. Cross-owner or wrong-purpose snapshots are rejected before an SSE stream begins.
- Recent code, errors, output, prompts, diagnostic answers, and snapshot content are absent from analytics, URL, logs, and release artifacts unless an approved one-request product payload requires them—and analytics never receives them.
- Old consumers remain green with additive producer fields; new flag-OFF consumers remain compatible during mixed rollout.
- OFF and ON frontend artifacts built from the same source SHA have distinct immutable digests; publish cannot mutate deployment state and promotion cannot rebuild the selected artifact.
- Analytics SDK blocking/failure adds zero navigation dependency and zero pre-permission requests.
- Landing cannot promote before the compatible app/backend flag-ON canary passes; reverse rollback preserves old deep links.

- Analytics and visual polish cannot validate an unstable activation contract. Database ownership, route identity, retained state, and terminal durability precede the final surface rollout.

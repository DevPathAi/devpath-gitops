# Mission Spine release control

Mission Spine releases use two immutable JSON documents. This avoids a self-referential hash: browser journeys cannot produce evidence hashes until they have consumed the release inputs.

The current integration state, external prerequisites, stop conditions, and operator checklist are recorded in the [2026-08-17 release handoff](../docs/mission-spine-release-handoff-2026-08-17.md). This document remains the permanent release-contract source of truth.

## Documents

1. `candidates/<release_id>.candidate-spec.json` is the canonical execution input. It contains only immutable source/image/config/environment inputs, `journey_harness`, and the quality case-catalog/build bindings; it contains no journey or quality result.
2. `releases/<release_id>.json` is the final release manifest. It binds the exact candidate-spec SHA-256 and the Home dist, privacy approval, AI release evaluation, two browser journeys, and seven distinct quality-evidence manifests: frontend visual, Home visual, frontend automated accessibility, Home axe/browser accessibility, manual NVDA, manual VoiceOver, and manual TalkBack. Every evidence reference repeats `candidate_spec_sha256`.

Both documents conform to `schema-v1.json`. `release_id` must match `^ms-[0-9]{8}-[a-z0-9][a-z0-9-]{2,40}$`. Promotion workflows accept only that ID. A digest, manifest path, branch, cluster, or Cloudflare deployment cannot be supplied as a workflow input. A candidate branch must descend from the exact `gitops.base_sha` and differ by only its canonical candidate file; after validation it must differ by exactly that candidate plus its canonical final manifest. Every production lane rechecks this branch shape before consuming secrets or mutating state.

No production candidate is checked in by this change because the real immutable images, successful workflow artifact IDs, model evaluation, browser journeys, quality results, and approvals do not yet exist. The synthetic files under `tests/release/fixtures/` are contract tests only and cannot be resolved by a release workflow.

## Candidate-spec contract

The candidate-spec binds:

- GitOps repository and exact `base_sha`, the one trusted legacy web tag plus its prior digest, and the one mutable path `apps/devpath-web/base/kustomization.yaml`;
- source SHA plus immutable OCI digest for every application service;
- Shared source, immutable version/JAR SHA-256, migration image, Flyway target `202608201002`, required V1011 validation, and the additive-retained rollback policy;
- frontend source, compiled app/config contract versions, distinct mission-OFF and mission-ON tag/digest pairs, selected ON digest, OFF rollback digest, and prior digest;
- Home source, deterministic canonical `dist.tar.gz` SHA-256, Cloudflare preview candidate ID, and current prior production ID;
- analytics privacy mode/region/retention/access/deletion inputs and the exact protected Documents source;
- actual AI primary/fallback model configuration, prompt and fixture hashes, the canonical-LF rendered GitOps configuration SHA-256, and the normalized private Ollama endpoint SHA-256 (never the endpoint itself);
- distinct staging/production identity, plus production-like journey origins and explicit Landing/app DNS overrides;
- exact repository/source SHA, catalog path/version/SHA-256, case count, and render/test input-provenance SHA-256 for all seven quality lanes; frontend v1 separates the common `leva.et13.catalog.v1` contract version from each lane's generated-file schema version, prebinds both the canonical input-provenance digest (sorted-key compact JSON with only `input_provenance_sha256` excluded) and the raw `provenance.v1.json` file digest, and binds one shared `leva.et13.projection-contract.v1` object whose digest is the canonical SHA-256 of the exact ordered 12-row fixture/capture-scope/source-widget/substitution matrix; both generated catalogs repeat that matrix and digest, and every generated case repeats its fixture's exact projection row; the visual catalog is exactly 96 cases (`Web` 48, `Admin` 16, `Mobile` 16, `dp_design` 16), and automated accessibility is exactly 24 (`Web` 12, `Admin` 4, `Mobile` 4, `dp_design` 4); the visual lane additionally prebinds an approved baseline set and approval digest; both frontend catalogs require `evidence_mode=release_ready`, `capture_surface=flutter_web_release_projection`, and `device_evidence=false`, so diagnostic/pending output is structurally unsealable and their `Mobile` cases cannot satisfy signed native-build or manual TalkBack evidence;
- Home's evidence-producer SHA separately from its rendered-product SHA, plus the rendered product-tree and font-manifest SHA-256 values; the Home runtime provenance is the SHA-256 of its sorted-key, compact JSON runtime object and the two Home manifests must bind the same catalog and render inputs;
- one protected, candidate-prebound signed-mobile build from the exact frontend source: repository/event/workflow blob, run/attempt, artifact ID/name/archive digest, and the exact `build-provenance.v1.json`, APK, and ad-hoc IPA paths and raw SHA-256 values; the provenance fixes the Flutter/Dart/Android/iOS toolchains, `USE_MOCK=false` production endpoints, source `pubspec.lock` and mobile version, verified organization signing classifications, and the two protected signing approvals without claiming Play/App Store distribution; VoiceOver must repeat the IPA/build pair and TalkBack the APK/build pair;
- three frontend-owned authoritative manual-AT catalogs and their raw-byte-bound static test-provenance documents: NVDA has the two approved physical Windows/Chromium Web cases, while VoiceOver and TalkBack each have the four approved physical-device Today, next-action, content-reading, and stale/offline cases; the catalog/provenance path, lane, AT/client/platform/artifact, ordered case IDs, all-pass policy, and all six distinct input hashes are fail-closed;
- exact producer-first order, 300-second sync detection, 900-second canary, Landing-last, 600-second reverse rollback budget, and retained backend/schema policy.

The browser harness receives the candidate file by absolute path and its SHA-256 out of band. It must parse those exact bytes. Journey evidence is `<artifact>/<journey>/evidence.json`, a non-empty JSON array whose rows contain exactly `route`, `step`, `result`, `duration_ms`, and `candidate_spec_sha256`. Both row order and the route/step pairs are allowlisted for the two approved journeys; free-form detail fields are rejected.

The dedicated read-only `.github/workflows/mission-spine-candidate.yml` workflow publishes the immutable candidate input without depending on the later validation/sealing run. A successful `workflow_dispatch` accepts only required string input `release_id`, proves that exact `release/candidate-${release_id}` is the single direct candidate-only commit on the candidate's still-current protected `gitops.base_sha`, runs the full candidate validator, and byte-copies the source to one root file named `candidate-spec.json`. It uploads exactly `${release_id}-candidate-spec-run-${run_id}-attempt-${run_attempt}` with bounded retention. The workflow has no protected environment, secret, write permission, deployment, or sealing path. Every downstream protected producer and GitOps itself enumerates all API pages, rejects stale rerun attempts and competing eligible run IDs, rehashes the raw API ZIP against metadata, safely extracts its sole regular root file, and proves the source blob, base/head workflow blobs, one-parent commit, and exact one-file compare before trusting the raw candidate SHA-256. The candidate binds `base_sha`; its head cannot self-reference and is authenticated transitively by those live facts.

## Final manifest and artifacts

All referenced GitHub artifacts must be unexpired and come from an exact successful run at the bound source SHA. Each reference binds repository, producer head SHA, run ID and attempt, canonical workflow path, the full workflow-blob SHA-256, artifact ID/name, selected evidence filename/hash, and candidate-spec hash; suffix/path lookalikes and branch-name-only provenance are rejected. Home dist is a fresh attempt-1 dispatch on current protected `master`, named `<release_id>-home-dist-run-<run_id>-attempt-1`, with exactly `dist.tar.gz` and six-field `evidence.json`. AI evaluation is a fresh attempt-1 dispatch on current protected AI `main`, named `<release_id>-ai-eval-run-<run_id>-attempt-1`; its exact one-file evidence repeats GitOps source/render/endpoint hashes and the protected `mission-spine-ai-release-eval` approval. GitOps independently materializes `apps/devpath-ai-svc/base` from `gitops.base_sha` and runs pinned kustomize v5.4.3 (archive `3669470…bcc7a7`, binary `1d6bae…c3a9a`) with the exact command `kustomize build apps/devpath-ai-svc/base`; noncanonical UTF-8/LF output, a hash mismatch, or runtime routing other than `qwen2.5:3b` through Ollama with the sole `claude-sonnet-4-6` fallback fails closed. Privacy approval is a fresh attempt-1 dispatch on current protected Documents `main`, named `<release_id>-privacy-approval-run-<run_id>-attempt-1`; its exact one-file evidence binds the candidate privacy fields and `approved_at == approval_effective_at ==` the protected job `started_at`. AI and privacy approvals require their exact environment/job and a configured direct user or active `member|maintainer` of a configured team. The authenticated approver may also be the workflow initiator when the AI-operated approval transaction below is used.

Frontend visual and automated-accessibility are one atomic `workflow_dispatch` pair from `.github/workflows/et13-evidence.yml`: both references must have the same head, workflow bytes, run ID, and highest successful rerun attempt, with unique names `<release_id>-frontend-visual-run-<run_id>-attempt-<run_attempt>` and `<release_id>-frontend-automated-a11y-run-<run_id>-attempt-<run_attempt>`. Protected baseline approval, mobile signing, manual-AT, Home dist, AI evaluation, and privacy approval are stricter: only `run_attempt=1` is sealable, a retry requires a fresh dispatch/new run ID/new protected approval where applicable, and every live run must be successful on its protected default branch. The signed artifact is `<release_id>-signed-mobile-build-run-<run_id>-attempt-1`; the atomic manual trio is `<release_id>-manual-{nvda|voiceover|talkback}-run-<run_id>-attempt-1`. Each embedded approval must match the exact protected environment and unique successful job, a configured user/team reviewer, and the job `started_at`; the authenticated reviewer may equal both run initiators. Run and artifact discovery reads every 100-row GitHub API page; multiple distinct eligible protected run IDs fail closed. Home visual and Home axe/browser accessibility are generated after candidate validation by the digest-pinned Home wrapper and uploaded as two sanitized manifests in one `<release_id>-home-visual-a11y-attempt-<run_attempt>` artifact owned by the exact GitOps `.github/workflows/mission-spine-validate.yml` run. Their run, attempt, head, workflow hash, and physical artifact ID must match the two journeys and validation attestation, while their selected filenames and hashes remain distinct. A normal Home `.github/workflows/ci.yml` push artifact is preflight-only and is rejected as release evidence. Since GitHub artifact metadata exposes the run ID but not the producing rerun attempt, each non-journey `evidence.json` result additionally carries exact positive-integer producer run/attempt data that must match the live run record; Home v2 manifests bind that identity through the shared validation-run artifact reference and live run lookup.

The validator proves the allowed `base → candidate-only → final-only` Git tree. The release gate downloads artifacts with `RELEASE_EVIDENCE_TOKEN` and verifies each exact selected-file hash and the exact allowed file set. The signed-mobile GitHub ZIP digest is independently rehashed before a bounded safe extractor rejects traversal, links, special files, duplicates, missing/extra entries, hash drift, and size drift; its only files are `build-provenance.v1.json`, `mobile/android/leva-release.apk`, and `mobile/ios/leva-release.ipa`. Signing must finish before any manual run starts, and the ad-hoc iOS profile must remain valid through signing, every manual approval, and sealing. Journey evidence uses the minimal row contract above. Quality evidence accepts only enumerated sanitized aggregates or Home's bounded per-case IDs, counts, viewports, and hashes. Each frontend lane package has exactly four canonical files: root `evidence.json`, `evidence/et13/generated/<lane>-cases.v1.json`, `artifacts/et13/provenance.v1.json`, and `artifacts/et13/<lane>-manifest.v1.json`. The verifier hashes the raw bytes of all three bound documents, recomputes the canonical input-provenance digest under the documented self-field exclusion, and requires the manifest's exact generated-case order, `passed` status, artifact path, nonzero per-case hash, and byte count. The automated lane is exactly `WCAG 2.2 AA` with zero critical/serious violations; the visual lane requires approved baseline bindings and zero pixel difference. `evidence.json` must include the post-run raw result-manifest SHA-256, while the candidate may prebind inputs only; an artifact-set hash and raw review material remain outside the sealed lane packages. Home v2 evidence binds its deterministic browser/container/font/theme/baseline provenance, requires zero accessibility violations at every severity, and must have an approved baseline before release. Raw screenshots, accessibility findings, notes, free-form content, and diagnostic output are not accepted. GitOps-owned journey and sealed-validation artifact names include `-attempt-<github.run_attempt>`, and sealing fails unless the read-only journey job ran in the current attempt. Because a document cannot contain its own hash, the successful validator run emits `<release_id>-sealed-validation-attempt-<run_attempt>`; that out-of-band envelope binds the final manifest's raw SHA-256, candidate SHA, validator head/workflow/run/attempt, and completed staging reverse duration. Promotion and rollback recompute the final raw hash and require that exact successful-run envelope.

The Home dist artifact contains exactly `evidence.json` and deterministic `dist.tar.gz`, whose hash must equal `home.dist_sha256`; both the outer ZIP and inner single-member canonical gzip/ustar stream are independently bounded and checked. The tar has only sorted unique regular files under `dist/`, requires `dist/index.html`, and rejects links, special files, duplicate/outside paths, trailing gzip members, noncanonical metadata/padding, and expansion beyond 100 MiB before deployment without rebuilding. Candidate, Home, AI, and privacy raw API ZIPs likewise require their exact root layout, metadata size/digest, regular files, safe paths, CRC, bounded expansion, and no duplicates, encryption, links, or special entries. Separately, the combined Home quality artifact contains exactly `visual-evidence.v2.json` and `a11y-evidence.v2.json`; each frontend lane uses the exact four-file sanitized package above; every remaining evidence artifact contains exactly its selected `evidence.json`. The producer may publish a separately named raw review artifact, but it is never discovered, referenced, or sealed by GitOps. Release evidence must never contain user-authored code, runtime output, error text, prompts, context snapshots, diagnostic answers, email, OAuth material, guest IDs, or credentials.

## Protected workflows

Configure required reviewers and `prevent_self_review=true` for every environment below. For an AI-operated approval, run `scripts/release/approve_pending_deployment.py` against exactly one pending environment. It snapshots the full mutable policy, temporarily sets only `prevent_self_review=false`, approves the authenticated pending deployment, restores the original policy in `finally`, and verifies the restored policy plus exact `main` branch rule. The protected job then queries the live environment and fails unless `prevent_self_review=true` has already been restored. A missing approval, stale run, rerun attempt, wrong reviewer, relaxed live policy, or restore failure remains fail-closed.

| Environment | Purpose | Required secrets |
|---|---|---|
| `mission-spine-staging` | read-only Home journeys, trusted seal, exact OFF→ON validation, reverse rehearsal | `MISSION_RELEASE_CONTROL_TOKEN`, `MISSION_SYNTHETIC_PROBE_TOKEN`, `STAGING_KUBECONFIG_B64`, `RELEASE_EVIDENCE_TOKEN` |
| `mission-spine-production-off` | verify migration and all service evidence, promote exact digests, then approved OFF digest | `RELEASE_EVIDENCE_TOKEN`, `PRODUCTION_KUBECONFIG_B64`, `MISSION_SYNTHETIC_PROBE_TOKEN`, `MISSION_SPINE_GHCR_READ_ACTOR`, `MISSION_SPINE_GHCR_READ_TOKEN`, `GITOPS_RELEASE_APP_ID`, `GITOPS_RELEASE_APP_PRIVATE_KEY` |
| `mission-spine-production-on` | separate manual ON approval, ≤5m sync, 15m canary, and final service re-observation | `RELEASE_EVIDENCE_TOKEN`, `PRODUCTION_KUBECONFIG_B64`, `MISSION_SYNTHETIC_PROBE_TOKEN`, `MISSION_SPINE_GHCR_READ_ACTOR`, `MISSION_SPINE_GHCR_READ_TOKEN`, `GITOPS_RELEASE_APP_ID`, `GITOPS_RELEASE_APP_PRIVATE_KEY` |
| `mission-spine-production-landing` | verify completed ON canary, then deploy Home dist last | `RELEASE_EVIDENCE_TOKEN`, `CLOUDFLARE_API_TOKEN` |
| `mission-spine-production-rollback` | authenticate Landing evidence, restore Landing prior, web OFF, then web prior while retaining services/schema | `RELEASE_EVIDENCE_TOKEN`, `PRODUCTION_KUBECONFIG_B64`, `CLOUDFLARE_API_TOKEN`, `MISSION_SYNTHETIC_PROBE_TOKEN`, `MISSION_SPINE_GHCR_READ_ACTOR`, `MISSION_SPINE_GHCR_READ_TOKEN`, `GITOPS_RELEASE_APP_ID`, `GITOPS_RELEASE_APP_PRIVATE_KEY` |

`RELEASE_EVIDENCE_TOKEN` needs Actions/Contents read access to every producer and GitOps plus organization Members read access for configured-team membership proof. Producer GitHub Apps need the same least-privilege reads for repositories they authenticate. `MISSION_SYNTHETIC_PROBE_TOKEN` authenticates the release-specific readiness endpoint. `CLOUDFLARE_API_TOKEN` needs Pages Write. Missing secrets, artifacts, model results, environment protection, cluster state, or deployment identity fail closed.

### Order

1. `mission-spine-validate.yml` validates the candidate-spec and GitOps base CAS in a read-only job, checks out the exact sealed Home SHA without persisted credentials, verifies the canonical candidate's raw bytes/out-of-band hash, runs Home's digest-pinned local production-dist visual/a11y wrapper with those inputs, uploads the exact two sanitized manifests, and then runs exactly Home's two live release journeys against the same candidate bytes/hash. The external Home code never runs with `contents: write`, and the visual/a11y step receives no live credential. A separate trusted job downloads all three current-run artifacts by exact ID, discovers the remaining successful source-pinned artifacts, validates and seals only the final manifest, then validates live staging prior identity, OFF/ON, and ON→OFF→prior within 600 seconds.
2. `mission-spine-promote.yml` runs only from protected current `main`. The first approved dispatch authenticates migration evidence, applies or reuses the exact migration child, atomically promotes the changed subset of nine service digests, verifies all nine Argo/Kubernetes runtimes, and commits mission OFF. A fresh separately approved dispatch starts from the durable OFF phase, re-authenticates compatibility and service evidence, commits mission ON, and holds the full 900-second canary before one final all-service observation.
3. `mission-spine-landing-last.yml` runs from protected current `main`, materializes the sealed candidate/release as data only, and requires the completed trusted promotion/canary artifact and exact migration/service/OFF/ON chain. Wrangler 4.123.0 is installed from the committed npm integrity lock only after the production environment approval. The job verifies Cloudflare prior or exact same-release retry state, adds a content-addressed public dist marker, deploys without rebuilding, re-authenticates unchanged main/release/canary state, and emits run-scoped Landing evidence.
4. `mission-spine-rollback.yml` shares the non-preemptible production lease with promotion and Landing. It authenticates the exact Landing artifact and referenced canary before the first Cloudflare mutation, safely resumes from durable migration/service/OFF/ON/rollback phases, restores Landing prior first, changes web through OFF when necessary and then prior, re-observes retained services, and finally rechecks that Landing prior is still current. Additive service APIs and V1011 remain in place.

Normal non-force pushes provide the final branch CAS: any `main` drift makes the release commit non-fast-forward and fails. The scripts additionally compare `origin/main` to the authenticated durable phase before every mutation and verify the exact promotion chain before Landing or rollback. Staging has one global concurrency lock. Promotion, Landing-last, and rollback share one production lock across release IDs with `cancel-in-progress: false`; a new dispatch cannot cancel an approved in-flight production mutation.
